# 공통 네트워크와 팀원 사용 기준

운영 VPC와 예약 대역을 구분한다. 새 연결 전에는 온프레미스·VPN·Azure CIDR 중복 여부를 확인한다.

| 위치 | 네트워크 | 서브넷 (두 칸이면 AZ A/B 순서) |
|---|---|---|
| AWS 서비스 | `10.10.0.0/22` | 앱·내부 ALB `10.10.0.0/24`, `10.10.1.0/24`; 퍼블릭 `10.10.2.0/27`, `10.10.2.32/27`; DB `10.10.2.64/27`, `10.10.2.96/27` |
| AWS 관리 (오사카) | `10.40.0.0/16` | 관제 VM `10.40.0.0/27`; 이전 서울 관리 `10.20.0.0/24`는 폐기 |
| Azure DR (주소 예약만) | `10.30.0.0/24` | VM `10.30.0.0/27`, MySQL 후보 `10.30.0.32/27` |

서울 퍼블릭 서브넷은 서비스 IGW, 두 앱 서브넷은 기존 `2a` NAT를 기본 경로로 사용한다. 앱 서브넷에서 오사카 `/27`로 가는 트래픽만 리전 간 피어링을 탄다. 서울 DB는 로컬 경로만 사용한다. 오사카 관제 서브넷은 IGW 기본 경로와 두 서울 앱 `/24`로의 반환 경로를 사용한다.

NAT를 한 AZ에만 두면 AZ마다 배치하는 것보다 NAT 시간 요금과 퍼블릭 IPv4 주소 비용을 줄일 수 있다. 다만 NAT 데이터 처리 요금은 발생하며, 두 번째 AZ의 앱 트래픽에는 AZ 간 전송 요금도 발생할 수 있다. NAT 또는 첫 번째 AZ에 장애가 나면 두 앱 서브넷 모두 인터넷 송신 경로를 잃는다. AZ 장애 시에도 송신이 필요하면 AZ마다 NAT를 두고 앱 서브넷이 같은 AZ의 NAT를 사용하도록 라우팅 테이블을 분리한다.

관제 VM은 Ubuntu 24.04이며 기본 운영 접속은 오사카 SSM이다. 피어링·포트별 범위와 전환 검증은 [VPC 2 운영 절차](envs/aws-prod/OSAKA-VPC2.md)에 있다.

팀원은 동일한 `aws-prod` 루트에서 공통 모듈의 VPC·서브넷 출력을 자기 모듈의 입력으로 연결한다. 개인별 VPC를 다시 만들거나 실제 AWS ID를 Git에 기록하지 않는다. 루트 출력은 `service_vpc_id`, `management_vpc_id`, `public_subnet_ids`, `app_subnet_ids`, `db_subnet_ids`, `management_subnet_id`다.

## CIDR 선정 근거

`10.10`(서울 서비스), `10.40`(오사카 관제), `10.30`(Azure 복구 예약)을 분리한다. 서울 관리용이었던 `10.20`은 사용하지 않는다.

| 대상 | 선정 기준 |
|---|---|
| 퍼블릭: AZ당 `/27` | 첫 번째 퍼블릭 서브넷에 NAT를 배치한다. 내부 ALB는 이 두 서브넷이 아니라 앱 `/24` 두 곳을 사용한다. ALB 확장을 위해 해당 앱 서브넷마다 빈 IP를 최소 8개 확보한다. [AWS ALB 서브넷 기준](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/application-load-balancers.html#subnets-load-balancer) |
| EKS 앱: AZ당 `/24` | 기본 VPC CNI는 노드뿐 아니라 Pod에도 VPC 주소를 할당한다. `/24`는 AWS 예약 주소 5개를 제외하면 251개를 사용할 수 있다. 이는 Pod 251개를 보장한다는 뜻이 아니다. 목표 노드·Pod 수가 정해지지 않아 배포 시 일시 증가와 CNI 예비 IP까지 고려해 여유를 둔 값이다. |
| RDS: AZ당 `/27` | 일반 리전의 DB 서브넷 그룹은 서로 다른 AZ 두 곳 이상을 포함해야 한다. `/27`은 AZ당 사용 가능 주소 27개를 남기는 팀 선택이지 RDS 최소 크기가 아니다. 서브넷 두 개 자체가 Multi-AZ DB를 생성하지도 않는다. |
| 오사카 관리 `/16`, Azure DR 예약 `/24` | 오사카와 Azure의 주소 충돌을 피하고 각 환경에서 당장 필요한 `/27`만 사용한다. |

**부모 VPC 계산에는 사용 가능 IP가 아니라 서브넷 전체 주소 수를 쓴다.** 앱 `256 × 2` + 퍼블릭·DB `32 × 4` = 640개이므로 `/23`(512개)에는 들어가지 않는다. 현재 `/22`(1,024개)에서 384개는 아직 서브넷에 할당하지 않은 주소다. `/27`은 32개 단위여서 `10.10.2.0`, `.32`, `.64`, `.96`이 연속된 서브넷의 시작점이다.

**재검토 기준:** EKS 규모가 정해지면 평균이 아닌 AZ별 최대 동시 IP 수요(노드, Pod, CNI 예비분, 롤링 업데이트 여유)를 산정한다. AZ당 123개로 충분하다면 앱 `/25` 두 개도 후보가 된다. 그 경우 총 384개 주소가 필요해 서브넷을 다시 배치하면 서비스 VPC를 `/23`으로 줄일 수 있다. 현재 코드 변경안은 아니다.

## 운영 배포 전 확인

- 올바른 AWS 계정·배포 역할, 서비스 리전·AZ 두 개 및 기존 CIDR과의 비중복을 확인한다.
- [공유 S3 backend](STATE.md) 버킷과 버전 관리, 잠금 권한 및 기존 state 유무를 확인한다.
- 배포 담당자만 최신 main으로 실제 plan을 검토하고 같은 plan을 적용한다. 재계획에서 변경이 없어야 실제 배포 검증 완료다. 로컬 mock plan 성공은 실제 배포 증빙이 아니다.
